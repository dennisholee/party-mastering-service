# Party Mastering Service

A standalone reference microservice for **bank customer data mastering** in the
**Party** domain, built with:

1. an OpenAPI 3.1 contract;
2. Java generated by OpenAPI Generator 7.27 (`spring` generator, delegate pattern);
3. Spring Boot 4.1 / Java 21;
4. a Party model that represents an individual customer (golden record,
   identifiers, contact points, addresses, documents and consents).

Data-level **entitlement**, response **masking** and request **data-quality**
controls are enforced by the controls sidecar, following
[`controls-core/docs/SIDECAR-GUIDE.md`](../controls-core/docs/SIDECAR-GUIDE.md).
The application implements business mastering only.

> This is a new, self-contained demo repository. It consumes a sibling
> `controls-core` checkout for the sidecar tools/binaries but does not modify
> it. Where the adoption guide was incomplete, the gap and the deferred
> upstream action are recorded in
> [`docs/GUIDE-COVERAGE.md`](docs/GUIDE-COVERAGE.md) (current) and the
> [archived adoption findings](docs/archive/ADOPTION-FINDINGS-2026-11-08.md).

## Status

`v0.1.0` reference demo, verified against `controls-core` `v0.41.0`
(Envoy 1.40 + ext_proc) with `make test` and `make test-signed` green:

- Java build and generated-code contract tests on Spring Boot 4.1;
- EOL checks for Spring Boot, Generator, Alpine and Envoy;
- registry schema validation against `controls-core/contracts`;
- registry drift, OpenAPI coverage and bundle checks;
- real Envoy + ext_proc contract tests for allow, deny, masking, DQ, rejected
  fields, self-description, unregistered routes and PIP outage;
- a **signed mode**: Ed25519-signed bundle verification plus required HMAC
  identity envelopes, with raw headers rejected;
- a **replica-lag matrix**: fresh reads allowed at the staleness boundary and
  denied with `stale_attributes` / `lag_unknown`;
- a **guide coverage matrix** and `make docs-check`/`make guide-smoke` so
  documentation completeness and command drift are testable.

## Architecture

```
client (local gateway stand-in: x-subject / x-claim-*)
   │
   ▼  :18007
party-mastering-sidecar  (Envoy + ext_proc)
   ├─ registry.json      route → party + mask policy
   ├─ rules.json         entitlement (default deny, deny-first)
   ├─ mask-policies.json field masking (incl. array wildcards)
   ├─ dq.json            request data-quality rules
   ├─ PIP :8082          party attributes + classification fixtures
   └─ audit/metrics
   │
   ▼  app:8080 (never published)
party-mastering-service (Spring Boot, generated API + delegate)
```

The sidecar calls the application only after identity, route binding, PIP
resolution, entitlement and DQ have succeeded. The application returns raw
golden-record values; Envoy applies the response mask on the way back.

## Domain

A **Party** is the mastered, golden record for an individual customer. The
model and invariants are described in [`docs/DOMAIN.md`](docs/DOMAIN.md).

| Area | Fields |
|---|---|
| Identity | `partyId`, `partyType=INDIVIDUAL`, `ssn`, `taxId`, `dateOfBirth` |
| Name | `legalName.firstName/middleName/lastName` |
| Contact | `contactPoints.email`, `contactPoints.phone` |
| Location | `addresses[]`, `region` |
| Documents | `documents[]` (type, number, issuing country) |
| Mastering | `status`, `segment`, `riskRating`, `version`, `updatedAt`, `sourceSystems`, `consents[]` |
| Entitlement | `ownerId`, `relationshipManagerId` (PIP-owned attributes) |

## API surface

| Method | Path | Operation ID | Control scope | Mask policy |
|---|---|---|---|---|
| `GET` | `/parties/{partyId}` | `get-party` | `party` (read) | `party.read` |
| `PUT` | `/parties/{partyId}` | `update-party` | `party` (write) | `party.update` |
| `POST` | `/parties/{partyId}/merges` | `merge-party` | `party` (write) | `party.merge` |
| `GET` | `/parties/{partyId}/export` | `export-party` | `party` (read) | `party.export` (non-JSON opt-out) |
| `GET` | `/parties` | `search-parties` | *excluded* (`x-controls-ignore`) | — |

`GET /parties/{partyId}/export` is a non-JSON route with
`x-allow-non-json: true`. The application emits only
`partyId,segment,status,region,version`; CSV cells cannot be masked, so the
service is responsible for never putting PII in the export. `GET /parties` is
an internal bulk search with no single resource identity. It is deliberately
excluded from the generated registry and therefore stays default-deny at the
sidecar. The application route still exists for the
internal console; the application port is not published.

See [`docs/CONTROLS.md`](docs/CONTROLS.md) for the route bindings, entitlement
matrix, exact masking outputs and DQ rule reference.

## Quick start

Prerequisites:

- Java 21+ and Maven 3.9+;
- Docker with compose;
- Go 1.27+ (builds the ext_proc/PIP Linux binaries);
- a sibling checkout at `../controls-core` (override with `CONTROLS_CORE=...`);
- ports `18007` (development), `18008` (signed) and `18009` (replica-lag) free.

```bash
mvn verify          # generate API/models, compile, run contract tests
make schema         # validate registry/mask/DQ fixtures against controls-core contracts
make docs-check     # links, anchors, documented make targets, guide coverage
make eol-check      # reject EOL bases, old framework/plugin versions, deprecated Envoy field
make gate           # docs + schema + drift + openapi-diff + controls-check + conformance
make test           # gate, build images, compose, end-to-end contract test, teardown
make test-signed    # render/sign a bundle, require HMAC identity, contract test
make test-lag       # dynamic stub PIP: boundary, stale, unknown, recovery
make test-lag-fixture # reference PIP + fixture resourceMeta: static matrix
make guide-smoke     # docs-check + gate + all four runtime suites
```

Run the stack interactively:

```bash
make up
curl -s -H 'x-subject: cust-1001' http://127.0.0.1:18007/parties/PTY-1001 | jq
make down

# signed bundle + HMAC identity on :18008 (see "Signed mode" below)
make signed
make down
```

If your Maven repository is local to the workspace (offline), override the
command instead of editing the Makefile:

```bash
make MVN="mvn -o" MVN_ARGS="-Dmaven.repo.local=.m2-repo" test
```

### Local identities

Raw `x-subject` / `x-claim-*` headers are a **development-only** gateway
stand-in. Production requires the signed `x-controls-identity` envelope
(`CONTROLS_IDENTITY_HMAC_KEY`), as described in the guide's phase 5.

| Caller headers | Outcome |
|---|---|
| `x-subject: cust-1001` | owner read of `PTY-1001` |
| `x-subject: rm-77` | relationship-manager read |
| `x-subject: u-ops-us`, `x-claim-role: ops`, `x-claim-region: US` | regional ops read |
| `x-subject: u-compliance`, `x-claim-role: compliance`, `x-claim-clearance: high` | compliance read/write |
| `x-subject: u-steward-us`, `x-claim-role: data-steward`, `x-claim-region: US` | update/merge `PTY-1001` |
| `x-subject: u-steward-eu`, `x-claim-role: data-steward`, `x-claim-region: EU` | update `PTY-2002` is denied (BLOCKED deny rule) |
| `x-subject: u-2` or no identity | `403` default deny |

### Signed mode

`make signed` renders the flat `controls/` fixtures into a bundle, generates an
Ed25519 key pair, signs the bundle, verifies it, and starts a second stack on
`:18008` with `allowUnsigned: false`, only the public key mounted, and
`CONTROLS_IDENTITY_HMAC_KEY` set. Any direct `docker compose -f
compose.signed.yaml` command must export that key; the make targets set it for
you. Every request must then carry a valid
`x-controls-identity` envelope; raw `x-subject`/`x-claim-*` are ignored.

Mint a local envelope with the stdlib-only helper:

```bash
export CONTROLS_IDENTITY_HMAC_KEY=party-mastering-local-identity-key-change-me
TOKEN=$(python3 tools/sign_identity.py \
  --subject u-ops-us --claim role=ops --claim region=US)
curl -s -H "x-controls-identity: $TOKEN" http://127.0.0.1:18008/parties/PTY-1001 | jq
```

`make test-signed` runs the signed contract tests: owner/RM/ops/compliance
allow, signed steward update, cleartext SSN rejection, and denial of missing,
tampered, expired and wrong-key envelopes (`403 identity_untrusted`).

### Replica-lag matrix

Two stacks exercise the same `x-max-staleness-seconds: 5` read:

- `make test-lag` (`:18009`) uses a local contract stub whose
  `lagSeconds`/`lagKnown` come from a state file. It proves the boundary,
  stale, unknown and recovery transitions on one endpoint.
- `make test-lag-fixture` (`:18010`) uses the **reference PIP** with
  `resourceMeta` in [`pip/attributes.json`](pip/attributes.json):
  `PTY-1001` reports lag 5 (allow), `PTY-2002` lag 6 (stale) and `PTY-3003`
  unknown lag. This proves the fixture metadata path without a custom PIP.

| Reported lag | `lagKnown` | Result |
|---|---|---|
| 2 or 5 | true | `200` (bound includes 5) |
| 6 | true | `503 stale_attributes` |
| any | false | `503 lag_unknown` |
| back to 2 | true | `200` recovery (stub stack only) |

The read journey uses `x-freshness: fresh`, so the sidecar bypasses its
attribute cache and observes each value immediately.

## What the contract test covers

The Maven tests validate the contract in two layers: `RegistryContractTest`
compares every annotation binding with the committed registry, and
`ControlsSchemaTest` validates `registry.json`, `mask-policies.json` and
`dq.json` against the normative schemas in `controls-core/contracts` (skipped
when the sibling checkout is absent; always present in `make gate` and CI).
`conformance/fixtures` adds an independent engine-level allow/deny/mask/DQ/
rejected-field suite; [`docs/GUIDE-COVERAGE.md`](docs/GUIDE-COVERAGE.md) maps
every guide section to its evidence and flags environment-only steps.

`test.sh` runs through Envoy + ext_proc (not against the engine directly):

| Case | Expected |
|---|---|
| owner, relationship manager, regional ops, compliance | allowed |
| unknown caller / missing identity | `403` |
| ops in the wrong region | `403` |
| unknown party | `404 resource_not_found` |
| owner read | exact masked `ssn`, `taxId`, `dateOfBirth`, email, phone, document number |
| steward update | `200`, version increments, response masked |
| owner CSV export | `200 text/csv`, non-sensitive columns only, no PII |
| non-owner / unknown CSV export | `403` / `404` |
| malformed JSON body | `400 invalid_json` |
| request body above 1 MiB | `413 request_body_too_large` |
| missing required first name | `403 dq_blocking:party.legalName.firstName.required` |
| invalid country in an address array | `403 dq_blocking:party.addresses.country.format` |
| invalid date / email / segment / version type | `403 dq_blocking:<rule>` |
| 45-char middle name (advisory DQ) | `200`, non-blocking violation logged |
| cleartext `ssn` | `403 rejected_field:ssn` |
| self-describing `_id` mismatch | `403 self_describing_id_mismatch` |
| BLOCKED party write by a steward whose region matches | `403 deny:party.write.blocked` (deny beats allow) |
| valid merge | `201`, duplicate id masked |
| invalid merge source id | `403 dq_blocking:party.merge.sourcePartyId.format` |
| merge source equals target | `400` (application cross-field rule) |
| `GET /parties` through the sidecar | `403 unregistered_endpoint` |
| application port | not published |
| PIP stopped | `503 pip_unavailable` |

`test-signed.sh` repeats the core allow/masking/rejection cases with a signed
envelope and adds: raw headers ignored, missing envelope, tampered signature,
expired envelope, wrong signing key, and an Ed25519-verified bundle with no
unsigned warning.

`test-lag.sh` covers the staleness bound, `stale_attributes`, `lag_unknown` and
recovery through the stub PIP. `test-lag-fixture.sh` covers the boundary,
stale and unknown cases through the reference PIP's `resourceMeta`.

## Generated code

`mvn generate-sources` produces:

- `com.example.party.api.PartiesApi` / `PartiesApiController` /
  `PartiesApiDelegate`;
- `com.example.party.model.*` (`Party`, `PartyUpdateRequest`,
  `PartyMergeRequest`, `PartyMergeResult`, `ErrorResponse`, nested types);
- `com.example.party.OpenApiGeneratorApplication` (Spring Boot entrypoint).

The service implements `PartiesDelegate` and a small mastering service. The
application entrypoint is intentionally the generated one to avoid a duplicate
`@SpringBootApplication`; if you prefer to own it, switch the generator to
`interfaceOnly` and add your own controller.

The generated API is never edited. `RegistryContractTest` fails the build when
the committed registry drifts from the annotations, including action, source,
attribute projection, freshness, masking and self-description bindings.
`ControlsSchemaTest` additionally validates the committed fixtures against
`registry.schema.json` and `mask-policy.schema.json`, so an id-casing or
attribute-shape mistake fails locally and in CI.

## Guide phase mapping

| Guide phase | Where it lives here |
|---|---|
| 1 — annotate the contract | `openapi.yaml`; `make registry`; `RegistryContractTest` |
| 2 — run locally | `compose.yaml`, `envoy/`, `pip/`, `sidecar.yaml`; signed mode in `compose.signed.yaml` |
| 3 — policy/DQ ownership | `controls/` fixtures are delivery-owned; service owns only annotations and registry |
| 4 — package/deploy | `Dockerfile`, `sidecar/Dockerfile`; production uses the Helm library |
| 5 — identity and PIP | raw headers in development; HMAC `x-controls-identity` in signed mode; PIP contract `1.0`, mTLS/keys in production |
| 6 — test | `mvn verify`, `make schema`, `make gate`, `make test`, `make test-signed`, `make test-lag` |
| 7 — rollout | signed bundle demo in `make signed`; key custody/canary remain production concerns |
| 8 — operate | decision logs and metrics from the sidecar; alert on PIP/DQ/stale/bundle |

## CI

[`.github/workflows/ci.yml`](.github/workflows/ci.yml) runs:

- **gate** on pushes and pull requests: `make gate`, including the docs check,
  schema, drift, OpenAPI, bundle and conformance gates;
- **e2e** on pushes to `main` and manual dispatch: `make test` (development
  headers), `make test-signed` (signed bundle + signed identity) and
  `make test-lag` (replica-lag matrix) through Envoy + ext_proc.

CI checks out `controls-core` next to this repository; set the repository
variable `CONTROLS_CORE_REPOSITORY` and, for a private checkout, the
`CONTROLS_CORE_TOKEN` secret. See [`ci/README.md`](ci/README.md).

## Non-goals and production notes

- The bundle in `controls/` is a **local fixture**; production rules come from
  the central `controls-rules` pipeline and are signed. `allowUnsigned: true`
  is development-only; `make signed` demonstrates the signed path, but locally
  generated keys are not production custody. Production keeps the private key
  in Jenkins credentials or an HSM and mounts only the public key.
- The PIP fixture is in-memory. Production PIPs use curated read-replica
  queries, mTLS and caller checks (guide phases 5 and 7).
- The app port is unpublished; a NetworkPolicy should admit the gateway only
  to the sidecar and the sidecar only to the PIP.
- The local demo image copies the sidecar entrypoint from `controls-core`
  `v0.41.0`; production should use the `controls-sidecar` Helm library and pin
  images by digest.
- The `x-controls-ignore`, DQ action/endpoint-scoping, mask-path and
  DQ-compilation gate gaps are fixed in the workspace `controls-core` checkout
  and recorded in [`docs/archive/ADOPTION-FINDINGS-2026-11-08.md`](docs/archive/ADOPTION-FINDINGS-2026-11-08.md).
  The demo no longer needs its earlier filtered-spec or `partyMerge`
  workarounds.
